# Bunting desktop app instructions

Scope: `apps/bunting-desk/**`. Decision record: ADR 0050.

- This app is a participant client, never a market authority. It never links `bunting-engine`, never matches, infers fills or edits account state. Everything it shows comes from committed BNP reports and feeds.
- It speaks BNP through `packages/bunting-client` only. No FIX feed fallback, no side channel, no REST/WebSocket/browser surface (ADR 0031).
- It renders the shared client state crate built with the TUI. Do not grow a second model here; ask for changes to the shared crate through the coordinator.
- Realism (ADR 0035): every order names its venue (no default router); each venue's book is shown as its feed reported it, never merged; latency shown is measured, never smoothed or estimated; order entry and the kill switch go straight to the I/O thread with no UI-side delay or batching.
- Local play (`--local`) joins the one shared practice venue for this machine (`bunting_trading_state::local_venue::join_or_start`): the first client starts the loopback `bunting server` detached, later clients (desks and TUIs) join it, each claiming one of eight funded participant identities by advisory lock (`--participant N` claims exactly N). The server is never a child whose fate follows one desk: it stops only when the last claim is released, and then only after its PID is verified against `venue.json`, its live BNP port and (on Linux) its command line. Never stop any other process. A server left behind by crashed clients is rejoined, or restarted when its configuration no longer matches.
- Keep collections bounded and tables virtualized; a live feed must never grow an unbounded element tree.
- Panes are `PaneKind`s (`src/panes.rs`, each with `min_size`/`default_size`): each can be opened any number of times, and its `name()` is written into saved screens, so never change one. Screens (saved views) and their templates live in `src/layouts.rs` (layout file v4); bump `LAYOUT_VERSION` when a saved screen could no longer load — older files are renamed to `layouts.v3.json`, never deleted.
- The canvas of floating windows is `src/canvas/` (ADR 0051): pure geometry (snap, clamp, tile, cascade, edge hit-testing) in `canvas/geometry.rs` with no GPUI types in its API and unit tests; the window manager in `canvas/mod.rs`; and `WindowFrame` in `canvas/frame.rs` — the one 28 px title strip (icon, title, instrument chip, actions). Panes draw no second title. Frame styling uses theme tokens only (no literal colours), sizes on a 4 px grid, 6 px window radius, and a shadow only on the focused window; title text and icons are vertically centred (`items_center`).
- Commands are GPUI actions in `src/actions.rs`: bind keys there, list them in the palette (`Workspace::palette`) and handle them in `Workspace::with_actions`, so a key, the palette and a button run the same code. One-click gestures are pure functions in `src/one_click.rs` (unit-tested); every one-click order names the clicked book's venue.
- Fonts: SF Pro only through the macOS system font (never bundle it); Inter and Source Serif 4 are bundled under the OFL with provenance in `assets/fonts/README.md`. Titles use `theme::serif`/`pane_title`, numbers `theme::tabular()`.
- Components come from `gpui-kit` (exact pin). Write GPUI code only for market-specific composition. Adapt source only from Apache-2.0 or MIT projects and record repository, commit and path. Zed's `crates/ui`, Coop, Zorite (GPL) and Rox (AGPL) are references only.
- This directory is its own Cargo workspace with its own `Cargo.lock` and `rust-toolchain.toml` (Rust 1.97), excluded from the root workspace. Run `tools/check_desk.sh` from the repository root; the root's seven gates do not build this app.
- Compilation and headless window tests are not visual acceptance. Say so when reporting.
