## Slice 0a — Trade accounting and simulation reconciliation

- Code commit: [`054a7d34944a68847152e2d961286985f57e0bff`](https://github.com/andrewkoumoudjian/bunting/commit/054a7d34944a68847152e2d961286985f57e0bff)
- Scope: `packages/ledger`, `packages/bunting-engine`, and focused tests. No matcher, host, schema, or application replacement.
- `Ledger::settle_trade` stages cash, reservations, and both signed inventory effects before mutation; invalid releases must not debit the other party.
- `PortfolioLedger::settle_trade` now journals balanced buyer/seller cash at execution price, tracks signed position basis and realized P&L for each fill, and marks affected holdings to the execution price. Position deltas and postings are checked before commit.
- `PortfolioLedger::net_liquidation_value` computes cash plus marked open-inventory value (basis + unrealized P&L); realized gain/loss is already in settled cash and must not be added again. Journal posting now stages only touched balances instead of cloning full history.
- `SimulationState::post_trade` makes matched fills visible to the simulation ledger. Simulation fine/cashflow/facility effects are reflected in the legacy risk-facing ledger projection before `transition_simulation` returns.
- The existing scalar participant initial-cash/account contract cannot represent multiple settlement currencies. Economic simulation scenarios with mixed settlement currencies now fail closed, pending a multi-currency risk account model.

### Known limitations and decision log

1. **Not yet a single ledger of record.** `Ledger` remains a staged matching/risk reservation projection; `PortfolioLedger` is the economic simulation journal. Matching-only legacy scenarios without economic instrument metadata continue to omit portfolio trade postings. A subsequent migration must establish a single authoritative economic state and deterministic restoration rules.
2. Positions seeded at run creation currently have no priced cost basis or mark. Fill-affected positions are marked to execution price; other positions remain unmarked until explicitly marked. Full portfolio NLV and scoring cannot be certified without scenario-defined initial inventory cost/mark policy, corporate actions, FX and fee treatment.
3. `TradeSettlement` still represents zero-fee immediate settlement. Clearing, margin, cash scheduling, borrow and multi-day marks are separate future dependencies.
4. Run transitions still clone the full state and books, and the origin store still rewrites complete JSON on every committed command; these are not optimized by this slice.
5. Legacy snapshot and transcript golden tests may need regeneration through **verified replay** after accounting semantics change. Do not hand-edit checksum goldens or relax deterministic assertions.
6. Venue-specific commands and market data are still incomplete for cross-listings. ADR 0028 remains **proposed**. Existing ADRs 0018/0019/0022–0025/0027 remain binding.

### Next dependency-ordered implementation

Complete the unified ledger migration, including a versioned initial mark and position-basis policy and legacy projection compatibility. Then introduce explicit `ListingKey` in order admission, public depth and trade events while retaining instrument-level portfolio aggregation. Verify focused tests before measuring or changing the live-book and origin hot paths.

## Slice 3 — Breaking order-identity overhaul (single allocator, no legacy)

**Decision:** No backward-compatibility path, no preservation of numeric order-ID parity and no opportunistic truncation. All accepted orders, whether the canonical external `OrderId` is a small integer or an opaque 128-bit transport ID, receive one monotonically increasing per-run `u64` internal matcher ID.

Implemented:
- `RunState.next_upstream_order_id` is the single run-wide allocator; `RunState.upstream_to_canonical: BTreeMap<u64, OrderId>` is the complete persisted reverse index of all orders, not just aliases.
- The allocator runs only after risk validation; it advances exactly once per accepted order. The candidate transition either persists the new counter/index with its matcher snapshot and event batch or discards all changes.
- Maker fill attribution always resolves the returned upstream ID through the indexed reverse map; cancels always use `OwnedOrder.upstream_order_id`. `OrderId` continues to be the exact externally supplied 128-bit identity, with no hash truncation or accidental renumbering.
- `RunState::validate` checks map cardinality, bijection, monotonic bounds, nonzero IDs and ownership consistency. Snapshot round-trip and replay tests cover full-width IDs, small IDs, multiple fill events, later cancel and recovered sequence.
- `ENGINE_VERSION = 2`, `ENGINE_SNAPSHOT_VERSION = 2`. Pre-v2 snapshots are rejected with `UnsupportedVersion`. The pre-envelope migration path `LegacyRunState` and the `from_persisted_json` fallback were **deleted**; Worker D1 loading calls strict `from_json` only. A v1 persisted run must be archived or discarded and recreated using the new protocol, never silently upgraded.
- Removed the `to_upstream_order_id` direct projection and its out-of-range error. No old-ID compatibility branch remains.
- No changes to the upstream OrderBook-rs authority, trade/accounting semantics or FIX external order-ID fields.

Main-branch commits:

## Slice 6 — Native append-only origin, bounded checkpointing and writer lease

**Scope:** durable native file origin only; the Worker D1 origin remains a separate optimistic SQL transaction backend. This slice does **not** eliminate the ordinary engine's clone-and-restore matching hot path and does not establish a zero-copy, always-live matcher.

- `04e3d25de62757d23a8635f84a649922aeac8da9`: clean up earlier Worker venue-routing Clippy failures by extracting focused reporting and listing helpers.
- `13657ae9722a150fe08faa10d869eb783ad54c4c`, `a7ca2646884207722ce14d4fdcba727a3c199bdd`: version-1 append-only record framing uses `BUNTWAL1` magic, eight-byte LE length, SHA-256 digest and strict serde commit record. A complete record is verified before replay. A short final header/payload is truncated as a crash tail; a complete invalid checksum/version/record fails recovery closed. Every record carries the complete candidate `RunState`, canonical events, command fingerprint/ID, result and client idempotency key. A 256 MiB individual record limit bounds allocation; no compression is claimed.
- `db9fbe660d1919079cc765181e6b14c67430a500`: `FileOriginStore::commit` validates version/cursors/idempotency and capacity, appends plus syncs the journal, then applies the durable record to live memory. No full `FileState` clone or historical event-file rewrite on each order. A synced journal record may be acknowledged even if best-effort later compaction fails.
- `3662f2e37301cab283fe187453fd247abcac3f7a`: store is poisoned after an ambiguous journal write and requires process restart/replay before further reads or commits. Explicit checkpoint API writes the complete file with temporary-file fsync, atomic rename and parent directory fsync on Unix; journal truncation follows successful durable checkpoint. Automatic checkpoint attempted every 128 committed commands.
- `0106e156ee555c29194bb50480d7c02838cb3de9`: regression tests prove ordinary commits remain in journal while original genesis checkpoint is unchanged, exact restart recovery, explicit checkpoint compaction, idempotent retry, incomplete-tail truncation, and rejection of complete tampered frames.
- `6afd7a3ef977452c97419c86ac55883e4d51d4c4`, `c5f73805780994b4ed88d2d88213fcf83ba1950a`: a safe Rustix nonblocking `flock` lease on a persistent sibling `.lock` file is held across all clones of the native origin until the last handle drops. Concurrent independent opens of the same path are rejected. This implementation deliberately refuses non-Unix durable file mode rather than silently admitting unprotected writers. Callers must not unlink the lock file while serving.
- Recovery reads a checkpoint and journal under the writer lease, replays only complete verified new records, and checks all recovered engine/event/command invariants. Frames already included in a checkpoint are checked for matching idempotency facts rather than reapplied; this supports a crash between atomic checkpoint replacement and journal compaction.

**Evidence:** initial native run [37732771598](https://github.com/andrewkoumoudjian/bunting/actions/runs/37732771598) passed engine, browser/FIX, and the expanded native origin/FIX-parity tests; both jobs stopped at rustfmt. The exact formatting fixes have been applied subsequently. Full Clippy/workspace tests on the final source commit are required.

**Known constraints:** journal records serialize the **current entire candidate run state** per committed order; the old file store serialized the whole growing run/command/event history instead. This reduces growth-related rewrite work but does not prove throughput or solve matcher restore costs. Journal length is limited by the maximum number of commands between 128-command checkpoints; a byte-triggered compaction limit and storage-capacity policy are future work. Exclusive locking is advisory and path-based on Unix, not a distributed consensus system. Checkpoint and journal must be backed up/recovered as a pair. No correctness claims across networked or exotic filesystems. Do not use file mode on multiple machines.

## Slice 9 — One authoritative economic ledger (2026-10-08)

**Problem.** Fills settled into `Ledger` (cash/holdings/reservations) and, only when a scenario declared economic instruments, separately into `simulation.portfolio_ledger` (cost basis, P&L, journal). Simulation commands then overwrote the risk ledger from the portfolio ledger. Tenders, OTC deals and composites changed status only; scoring ranked only participants that had a private projection; marks were applied to every holder at score time; the journal grew without bound inside every committed state; risk rebuilt a `RiskState` map and scanned every owned order on each submission; fees, multipliers and multi-currency cash were unsupported.

**Implementation.**
- `packages/ledger` is rewritten as the single `Ledger`: per-(participant, currency) cash with reservation and cumulative fees, per-(participant, instrument) position with inventory reservation, open buy/sell counters, average cost basis, realized P&L and traded volume, per-instrument `InstrumentTerms` (currency, multiplier, shortable) and per-instrument marks. `settle(Fill)` stages both parties (or one party against the house), releases the filled part of each order's exact `Reservation`, charges fees, enforces funding for cash-constrained buyers and inventory for non-shortable sells, and leaves the ledger unchanged on any error. `reporting_value` converts per-currency NLV through explicit `FxRate` instruments and fails closed when a rate is missing. `PortfolioLedger`, the journal, `AccountProjection`/`HoldingProjection` and the sync code are deleted; committed events are the audit trail.
- `packages/risk-engine` is a pure `admit(limits, enabled, order, listing_terms, ledger, market_bound)` returning the reservation contract; open quantity comes from O(log n) ledger counters and is aggregated per instrument across venues. Unused `PortfolioRiskLimits`/`check_portfolio`/`RiskState` are removed. `RiskLimits.cash_constrained` (default true) selects funded versus RIT-style unconstrained accounts.
- Scenario schema v2 (`SCENARIO_SCHEMA_VERSION = 2`): root `instruments` (currency, kind, multiplier, shortable, opening mark — required for any opening position), `reporting_currency`, `fx_rates`; per-currency `initial_cash`; per-listing `FeeSchedule { taker_per_lot, maker_per_lot }` (RIT `TradingFee` / negative `LimitOrderRebate`); `simulation.starts_active`. Engine/snapshot version 3; earlier snapshots are rejected, not migrated.
- Engine: one `RunState.ledger`; `OwnedOrder.reservation`; `TradeExecuted` carries `buyer_fee`/`seller_fee`; orders are rejected unless the run lifecycle is active; accepted tenders settle against the house (`TenderSettled`) and accepted OTC negotiations settle bilaterally (`OtcSettled`) without moving the public mark; OTC responses alternate through an explicit `awaiting` party and settled deals cannot be broken; facility jobs convert positions with basis transfer; fines and cashflows post cash; scoring ranks every enrolled participant by reporting-currency NLV at last-trade marks. Composite orders and scheduled option exercise/delivery, which previously reported success without economic effect, now fail closed as `Unsupported`.
- Matcher adapter: OrderBook-rs 0.10.3 consumes an IOC's partial fills and then returns `InsufficientLiquidity`, discarding them (so any partially filling IOC failed the whole command). IOC is now submitted as GTC and its remainder removed in the same transition; an infeasible FOK is killed without touching the book. Non-resting remainders are detected from the book (`contains`) rather than assumed, so IOC/FOK remainders are no longer reported as `OrderRested`.
