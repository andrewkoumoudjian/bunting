# Engine implementation log — 2026-10-07

## Slice 0a — Trade accounting and simulation reconciliation

- Code commit: [`054a7d34944a68847152e2d961286985f57e0bff`](https://github.com/andrewkoumoudjian/bunting/commit/054a7d34944a68847152e2d961286985f57e0bff)
- Scope: `packages/ledger`, `packages/bunting-engine`, and focused tests. No matcher, host, schema, or application replacement.
- `Ledger::settle_trade` stages cash, reservations, and both signed inventory effects before mutation; invalid releases must not debit the other party.
- `PortfolioLedger::settle_trade` now journals balanced buyer/seller cash at execution price, tracks signed position basis and realized P&L for each fill, and marks affected holdings to the execution price. Position deltas and postings are checked before commit.
- `PortfolioLedger::net_liquidation_value` computes cash plus marked open-inventory value (basis + unrealized P&L); realized gain/loss is already in settled cash and must not be added again. Journal posting now stages only touched balances instead of cloning full history.
- `SimulationState::post_trade` makes matched fills visible to the simulation ledger. Simulation fine/cashflow/facility effects are reflected in the legacy risk-facing ledger projection before `transition_simulation` returns.
- The existing scalar participant initial-cash/account contract cannot represent multiple settlement currencies. Economic simulation scenarios with mixed settlement currencies now fail closed, pending a multi-currency risk account model.

### Verification status

Source-level focused tests added: trade cash conservation, position and realized-P&L arithmetic, invalid reservation rollback, maker/taker journal reconciliation, fine-to-risk consistency and snapshot roundtrip. **Test assertions are committed but are not evidence of passing execution.** Native Rust was not available in the connector execution environment. CI run [#262](https://github.com/andrewkoumoudjian/bunting/actions/runs/37684466232) stopped before tests because the pinned WASIX installer pulled `cargo-platform@0.3.3` requiring rustc 1.91, while root toolchain is 1.88. A narrow native-core CI job was added in the follow-up commit to obtain focused evidence without changing ADR 0027's production runtime decision.

### Known limitations and decision log

1. **Not yet a single ledger of record.** `Ledger` remains a staged matching/risk reservation projection; `PortfolioLedger` is the economic simulation journal. Matching-only legacy scenarios without economic instrument metadata continue to omit portfolio trade postings. A subsequent migration must establish a single authoritative economic state and deterministic restoration rules.
2. Positions seeded at run creation currently have no priced cost basis or mark. Fill-affected positions are marked to execution price; other positions remain unmarked until explicitly marked. Full portfolio NLV and scoring cannot be certified without scenario-defined initial inventory cost/mark policy, corporate actions, FX and fee treatment.
3. `TradeSettlement` still represents zero-fee immediate settlement. Clearing, margin, cash scheduling, borrow and multi-day marks are separate future dependencies.
4. Run transitions still clone the full state and books, and the origin store still rewrites complete JSON on every committed command; these are not optimized by this slice.
5. Legacy snapshot and transcript golden tests may need regeneration through **verified replay** after accounting semantics change. Do not hand-edit checksum goldens or relax deterministic assertions.
6. Venue-specific commands and market data are still incomplete for cross-listings. ADR 0028 remains **proposed**. Existing ADRs 0018/0019/0022–0025/0027 remain binding.

### Next dependency-ordered implementation

Complete the unified ledger migration, including a versioned initial mark and position-basis policy and legacy projection compatibility. Then introduce explicit `ListingKey` in order admission, public depth and trade events while retaining instrument-level portfolio aggregation. Verify focused tests before measuring or changing the live-book and origin hot paths.

## Slice 1a — Venue-targeted order admission and exchange market projections

- Implementation commit: `c74b25426e6bef519a0298a560fb45e876b3a439` (explicit route, listing tapes, optional venue on trade events); verification and accounting atomicity refinement in subsequent incremental commit.
- Added `CommandPayload::SubmitOrderAtListing { listing_key, order }`, explicitly requiring `listing_key.instrument_id == order.instrument_id` and a registered listing. Legacy `SubmitOrder` remains accepted only when instrument identity is unambiguous.
- Every newly matched trade embeds `listing_key: Some(ListingKey)`; old persisted events deserialize with `None`. Public trade projections now include optional venue ID but never disclose private counterparties.
- Each listing now has independent `market_by_listing` L2 and trade tape. The legacy instrument market record is a consolidated trade tape; its depth is retained only for an instrument with exactly one listing, to avoid falsely publishing an arbitrarily chosen venue's book as a consolidated view.
- Trade history prevalidates both venue and consolidated bar/volume capacity before either is mutated; no cloning of trade/depth history on each incoming fill.
- The same economic `InstrumentId` remains the account holding key across all venues. Cross-listing test exercises legacy ambiguity, independent books, venue-scoped trades and snapshot restoration.
- This is not a full v2 wire/API migration: FIX/browser order-entry adapters remain instrument-only, and no consolidated NBBO or cross-venue routing policy has yet been defined. The new canonical payload is additive; legacy event wire records remain readable.
- Prior accepted ADRs remain unchanged. ADR 0028 is still proposed. Next slice should expose explicit listing routing at authenticated ingress and venue-scoped market-data subscriptions, then improve the transaction/recovery hot path.
