# ADR 0034: Fair remote admission — distance neutral, implementation rewarded

- Status: **Superseded** by [ADR 0035](0035-real-life-latency.md) (2026-10-10): the owner chose a single real-life model in which real network delay counts and is never equalized. Kept as decision history.
  session that followed slice 15b. **Target — implemented in slices recorded
  in `docs/implementation-log/`.**
- Date: 2026-10-10
- Supersedes in part: ADR 0030 §1 (delay measurement), makes ADR 0030 §4
  (outbound equalization) mandatory, and changes ADR 0030's default mode.
  ADR 0030's continuous price-time matching, release formula, sequencer (§2,
  §3) and journaling (§5) stand.
- Depends on: ADR 0022, ADR 0029, ADR 0030, slice 14/15b journal.

## Context

The owner's requirement for remote competitions (hackathons, classes,
QUARCC rounds), 2026-10-10:

> The latency model must not punish people for being far from the server —
> physically, or at the connection level (IP routing, ISP, TCP handshake).
> Latency must not be able to be made artificially higher to gain an edge.
> It should reward people for a good client implementation.

ADR 0030 points the right way but leaves three gaps against that
requirement (*observed* in its text and in `simfix-session`):

1. **Inflation pays.** ADR 0030 estimates one-way delay from FIX
   TestRequest/Heartbeat round trips over a sliding window. The reply is
   produced by the participant's own code, so a client that answers slowly
   looks farther away and receives *more* credit. Worse, a carelessly
   written client (a heartbeat handler on a busy loop) gains by accident,
   which rewards bad implementation. A sliding window also lets a client
   calibrate low and inflate later.
2. **Inbound-only compensation still favors proximity.** If market data and
   execution reports leave the server at the same instant for everyone, the
   nearest client sees them first and its reaction is sent first; inbound
   compensation only removes half of the distance. ADR 0030 makes the
   outbound hold a mode detail.
3. **The host can penalize good clients.** The current session host reads
   one message, then blocks until it is processed, so a client that
   pipelines orders sees later orders stamped late. Server-side Nagle or
   per-connection serialization would penalize exactly the behaviors a good
   client uses.

## Decision

### 1. Fairness contract

In `equalized` (and `geographic`) mode the venue promises:

- **Distance neutral.** For any participant whose one-way network delay is at
  most the published `D`, the time at which a message reaches the book, and
  the time at which every outbound message reaches the participant, do not
  depend on that delay. What remains is estimation error (asymmetric routes,
  queueing jitter above the path minimum), which the rules state.
- **No gain from looking slower.** No participant can improve its admission
  order or data timing by making its connection appear slower, unless it
  forges kernel-level TCP behavior, and even then by at most
  `D − true one-way delay`. With kernel RTT, accidental slowness (slow
  heartbeat handling, delayed ACKs, Nagle, pauses) never earns credit; in
  `probe_only` deployments see §6.
- **Implementation rewarded.** With distance removed, the remaining
  difference between participants is their own processing time: how fast the
  client parses, decides and sends, whether it pipelines, keeps a warm
  connection, disables Nagle and uses the protocol efficiently. Those
  advantages are kept intact.

### 2. Delay estimate (replaces ADR 0030 §1)

For each connection the gateway maintains:

- `kernel_min` — the kernel's minimum TCP RTT for the socket (Linux
  `TCP_INFO.tcpi_min_rtt`, read through a safe netlink `sock_diag` query,
  since the workspace forbids `unsafe` outside bindings). It is computed from
  ACKs generated by the participant's operating system, which application
  code cannot delay, and it includes the handshake sample, so it exists from
  the first message.
- `probe_min` — the minimum RTT over **the connection's lifetime** from
  periodic FIX TestRequest probes (unpredictable `TestReqID`, monotonic
  microsecond send stamp kept server-side), and later BNP `Ping`/`Pong`.
  Probes are sent at logon (a short burst) and then at randomized intervals
  (50–150% of the configured interval), not only when idle, so a client that
  reads its socket periodically still answers some probes immediately and the
  lifetime minimum converges to its true RTT.

```text
d̂(c) = clamp( min(kernel_min, probe_min) / 2 , 0 , D )   # over available sources
```

Properties:

- **Minimum across sources**: inflating one source gains nothing; a client
  must inflate every source consistently.
- **Lifetime minimum (non-increasing)**: a connection cannot measure low and
  inflate later. It reconnects to re-measure (for example after a route
  change); a reconnect costs the participant time, so it is not free.
- **No samples → `d̂ = 0`**, never `D`. With kernel RTT available this case
  does not arise after the handshake.
- Each admission records which sources were present (`rtt_source`).

### 3. Venue time in both directions (ADR 0030 §2, §4 — now mandatory)

```text
inbound:   release(x)  = t_rx(x) + (D − d̂(c)) + L(p, v)
outbound:  send_at(m)  = t_commit(m) + (D − d̂(c)) + L(v, p)
```

So a message reaches the book at about `true send time + D + L`, and an
outbound message reaches the participant at about `t_commit + D + L`, for
every participant. Session-level messages (heartbeats, probes, logon,
resend) are never held: probes must measure the raw path. The outbound hold
queue is bounded per connection; overflow disconnects that connection, as the
committed-event distributor already does.

`D` is published before the round and never changes during it. Organizers
pick it from a practice round: the server's health output shows each
connection's `d̂`, sources and sample count, and warns when `d̂ ≥ D`
(that participant is disadvantaged by the excess). The default is
`D = 150 ms` one way, which covers about 300 ms RTT; every participant's
fastest see-and-react loop is then about `2D` plus their own processing.
That cost is the price of fairness and is published.

### 4. Server obligations

The host must not add delays that depend on client implementation:

- `TCP_NODELAY` on every server socket.
- `t_rx` is taken when bytes are read, before parsing; messages that
  arrived in one read share it.
- Admission is non-blocking: every message of a pipelined burst is admitted
  with its own `t_rx`; the reader never waits for execution.
- Results (reports, market data, rejects) come back through the held
  outbound path, never as an implicit reward for waiting.
- Rate limits are per participant, identical and published.

### 5. Modes and defaults

| Mode | When | Default |
|---|---|---|
| `equalized` | Remote events, single or multi venue | **yes** |
| `geographic` | A scenario wants simulated venue distance (cross-venue arbitrage); `L` comes only from the scenario table, never from real geography | opt-in |
| `physical` | All participants on one LAN; real latency counts | opt-in |

### 6. Residual risks (stated in the rules)

- **Deliberate ACK shaping.** A participant who delays its OS's pure ACKs
  *and* its probe replies, consistently from the first packet, inflates
  `d̂` by up to the shaping amount, gaining at most `D − true one-way delay`.
  This needs kernel-level traffic shaping and is visible in the published
  `d̂`, which organizers can compare with each team's registered location.
  No server-only measurement can rule it out, because every RTT depends on
  the client answering.
- **TLS terminated by a proxy (`probe_only`).** The kernel RTT then measures
  the proxy hop, so only probes are used, and a probe reply delay counts as
  distance. *Observed* in `tests/fair_admission.rs` during slice 15: a test
  client that read its socket only every ~50 ms was credited with that delay
  and beat a nearer client that had sent first. Randomized probe timing
  limits this for clients that read continuously, but a client that reads
  slowly (by accident or design) still gains up to its reading delay, capped
  at `D`. The rules require prompt TestRequest replies and prohibit
  deliberate delay; the health page flags outliers. The server refuses
  `kernel_and_probe` with a terminated TLS profile, because measuring the
  proxy hop would silently withhold all compensation. Competitive rounds
  should terminate TLS in-process (ADR 0031 target) to get kernel RTT.
- **Asymmetric routes and jitter.** `RTT/2` misattributes asymmetric delay,
  and queueing above the path minimum counts against whoever it hits. Wired
  connections minimize this; it is stated, not hidden.
- **Hosts without `sock_diag`** (WASIX, non-Linux) fall back to probes only,
  with the weaker inflation resistance. This is another input to the host
  decision (ADR 0033).

## Rejected alternatives

- **Trust client timestamps or TCP `TSval`** for per-packet send times:
  forgeable by the client.
- **Sliding-window minimum (ADR 0030)**: lets a client calibrate low, then
  inflate.
- **Adaptive `D` (largest current `d̂`)**: changes ordering mid-round and lets
  one inflating client slow everyone.
- **"Lowest ever seen for this participant" across connections**: punishes a
  participant whose network genuinely got worse mid-event.
- **Inbound-only compensation**: still lets proximity decide who reacts
  first.

## Validation

1. Two clients with injected one-way delays of 2.5 ms and 60 ms and identical
   reaction time reach the book in arrival-sequence order in `equalized`
   mode; the near client wins in `physical` mode.
2. With injected delays both ways, a client whose processing is 1 ms faster
   wins regardless of which one is far.
3. A client that delays heartbeat replies gains nothing when kernel RTT is
   available, and gains at most `D − true one-way` when it is not.
4. `d̂` never increases within a connection.
5. A pipelined burst keeps per-message `t_rx`; the server never sets
   `TCP_NODELAY` off.
6. ADR 0030 validation items 2 (replay determinism) and 4 (geography) still
   apply.

## Consequences

- The FIX session gains a probe API and reports echoed `TestReqID`s; the
  gateway keeps microsecond monotonic stamps (the session stays clock-free).
- The server gains a sequencer thread, per-connection outbound hold queues
  and a Linux `sock_diag` RTT reader; the ADR 0024 interval writer is retired
  when this lands.
- Admission records gain `rtt_source`; the journal already carries admission
  metadata (slice 15b).
